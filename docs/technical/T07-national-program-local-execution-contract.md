# National Program / Local Execution — first contract slice

The headquarters-owned `NationalProgramVersion` holds an opaque program ID, positive version, national objectives and mandatory requirements. Its collections are defensive read-only copies. `CenterProgramPlan` captures an explicit center ID, a reference to exactly one national version, a local title and local activities; it cannot mutate national goals or requirements. No goal counts, mandatory threshold, program calendar or center assignment are inferred.

This is **only a domain contract and executable invariant tests**. It is not a persistent registry, API, headquarters publishing permission, center membership check, local adoption authorization, approval, audit event or production-ready program workflow. Next implementation must introduce authoritative center identity and human-managed authorization, versioned persistence, then audited national publication and local adoption with tenant scoping. Do not expose mutation endpoints before those gates exist.

## Version registry foundation
`NationalProgramCatalog` provides an in-memory deterministic registry keyed by exact program ID and version. Duplicate versions are rejected; missing versions never fall back to latest. `CenterProgramVersionBoundary` verifies that local plans and adoption requests match the same existing national version and center. This is a pure testable domain foundation, not PostgreSQL persistence, publication approval, a trusted current registry, or authorization. A real command handler must combine authoritative registry state, verified identity, operation-specific permissions, transactional audit/outbox, and concurrency control before any write.

## Explicit publication boundary
A registered national version is **not** published by default. `NationalProgramPublicationIndex` records explicit metadata for a previously registered exact version; duplicate and unknown publications fail closed. `PublishedCenterProgramBoundary` requires publication plus exact national-version, center, and actor structural matching before considering a local adoption request. This is in-memory evidence modeling only: publication must ultimately be written transactionally by an authenticated, authorized headquarters human with auditable persistence. These pure checks must never be interpreted as sufficient authorization or as a live API workflow.
