# T02 — معماری فنی پایه کانون‌یار
وضعیت: DRAFT — پیشنهاد معماری برای بازبینی، نه مجوز شروع Code
تاریخ: ۲۰۲۶-۱۰-۱۱
مراجع: B01–B05A و T01 مصوب

## ۱. ساختار سامانه
- یک پلتفرم مشترک برای ۸۰ کانون، نه ۸۰ استقرار مستقل.
- سه تجربه React/TypeScript با فارسی/RTL: ستاد مرکزی، پنل واحد کانون با سطوح دسترسی، پرتال مخاطبان.
- Backend عملیاتی C# / ASP.NET Core با معماری Modular Monolith، مرزهای ماژولی مشخص و APIهای نسخه‌دار.
- PostgreSQL منبع حقیقت داده عملیاتی است. AI در Python/PyTorch صرفاً قابلیت پیشنهادی/تحلیلی ارائه می‌کند.
- هیچ ماژول عملیاتی برای اجرای قاعده کسب‌وکار یا تأیید انسانی به پاسخ AI وابسته و بدون جایگزین نمی‌شود.

## ۲. ماژول‌های دامنه و مالکیت داده
| ماژول | مسئولیت و مالکیت اصلی |
|---|---|
| IdentityAccess | هویت ارتباطی، عضویت کانون، مجوز مؤثر، تفویض، لغو و حسابرسی |
| CenterManagement | شناسنامه و تنظیمات کانون، تقویم و وظایف |
| NationalPrograms | تعریف نسخه‌دار ملی، الزامات ثابت، ابلاغ و تاریخچه |
| LocalPrograms | طرح اجرای بومی، برنامه محلی، اتصال فعالیت‌ها |
| Learning | دوره، کلاس، جلسه، مربی، ثبت‌نام و حضور |
| Events | رویداد، مسابقه، ثبت‌نام و نتیجه معتبر |
| Campaigns | پویش، مشارکت و پیشرفت |
| ContentWeb | سایت‌ساز، صفحه/فرم، محتوا، نسخه و انتشار |
| Audience | مخاطب، ارتباطات و مجوز/رضایت لازم |
| FinanceResources | اسناد مالی، منابع و تجهیزات؛ بدون فرض اختیار پرداخت |
| Crowdfunding | پروژه و ثبت مشارکت مجاز؛ پرداخت واقعی مشروط به قرارداد |
| Collaboration | همکاری و اشتراک منابع/محتوای مجاز بین کانون‌ها |
| EvaluationReporting | نماهای مجاز، شواهد، شاخص‌های مصوب و بازبینی انسانی |
| AIOrchestration | آماده‌سازی درخواست حداقلی، کنترل مجوز، ثبت نتیجه و بازبینی انسانی |

هر ماژول مالک داده و قواعد خود است. اتصال بین ماژول‌ها از قراردادهای مشخص داخلی/رویدادهای معتبر انجام می‌شود؛ دسترسی مستقیم دلخواه به جدول ماژول دیگر ممنوع است.

## ۳. چندکانونی و امنیت
- هر داده کانونی باید دامنه مالکیت مشخص داشته باشد؛ داده ملی و مشترک نیز دامنه و سیاست مستقل دارند.
- کنترل مجوز سمت سرور برای actor + operation + resource + center scope؛ نقش UI جایگزین مجوز نیست.
- آزمون اجباری جلوگیری از IDOR و عبور از دامنه کانون؛ کنترل لغو مجوز در درخواست‌های بعدی.
- برای گزارش ستاد، نماهای محدود و حداقل داده موردنیاز؛ داده حساس مخاطبان و خردسالان نیازمند مبنای قانونی، رضایت/نمایندگی و سیاست نگهداری مصوب است.
- راهبرد فنی تفصیلی جداسازی tenant (مانند row-level isolation و دفاع چندلایه)، نحوه اعمال آن در PostgreSQL و آزمون‌های آن باید در تصمیم فنی جداگانه تثبیت شود؛ فعلاً روش قطعی انتخاب نشده است.

## ۴. ارتباط و یکپارچگی
- APIهای HTTP نسخه‌دار برای سه تجربه کاربری.
- تراکنش‌های یک ماژول در محدوده داده همان ماژول؛ هماهنگی بین‌ماژولی باید رویداد معتبر، idempotency و شکست قابل بازیابی داشته باشد.
- عملیات طولانی، پیام‌رسانی، ذخیره فایل، cache، موتور گردش‌کار و ابزار observability در T01 به‌صورت قطعی انتخاب نشده‌اند؛ گزینه‌ها پس از نیازسنجی و آزمون انتخاب می‌شوند.
- فرم‌ساز و گردش‌کار قابل تنظیم نباید امکان دور زدن مجوزها یا خلق تأیید مالی/اداری جدید داشته باشند.

## ۵. قرارداد مرزی AI
- AI با Python/PyTorch زیرسامانه تخصصی است؛ مالک state رسمی، دسترسی‌ها، پرداخت‌ها یا معیارهای ارزیابی نیست.
- Backend پیش از فراخوانی، مجوز و دامنه داده را کنترل و فقط اطلاعات لازم را ارسال می‌کند.
- خروجی AI پیشنهاد/تحلیل برچسب‌دار است؛ تغییر داده رسمی یا انتشار، نیازمند اقدام مجاز و ثبت حسابرسی است.
- داده عملیاتی خودکار وارد Training نمی‌شود: داده مجاز → پالایش و بازبینی → Dataset نسخه‌دار → Training → Evaluation مستقل → Human Approval → Promotion کنترل‌شده.
- روش اجرای داخلی/اتصال، مدل، GPU، زمان پاسخ، هزینه و معیارهای ارزیابی هنوز بازند. از این سند سرویس خارجی، endpoint، token یا مدل معین استنباط نمی‌شود.

## ۶. قرارداد داده و گزارش
- ثبت داده در ماژول منبع یک‌بار؛ ارزیاب‌یار و ستاد نماهای خواندنی و قابل ردیابی مصرف می‌کنند.
- داده ناقص به صفر، نتیجه موفق یا امتیاز اختراعی تبدیل نمی‌شود.
- نسخه برنامه ملی، ابلاغ، طرح بومی، فعالیت و شواهد باید زنجیره ردیابی پایدار داشته باشند.
- رویدادهای حساس شامل عامل، زمان، دامنه و تغییر قابل حسابرسی‌اند؛ سیاست نگهداری و حذف نیازمند تصمیم معتبر است.

## ۷. کیفیت و دروازه‌های توسعه
- Unit / Integration / API contract / migration / tenant-isolation / concurrency / browser E2E / security tests.
- CI باید ساخت Backend و Frontend، lint، تست و بررسی migration را پوشش دهد؛ Stage و Production فقط پس از دروازه‌های رسمی.
- آزمون سراسری حداقل: برنامه ملی نسخه‌دار → ابلاغ → طرح بومی دو کانون مستقل → کلاس/رویداد → ثبت‌نام و اجرای واقعی → گزارش ستادی با شواهد.
- راه‌اندازی و آزمون هر ۸۰ کانون بخشی از معیار افتتاح کشوری است، نه تعهد به ۸۰ دیتابیس یا ۸۰ استقرار.

## ۸. تصمیم‌های باز قبل از طراحی اجرایی
1. نسخه دقیق .NET و قرارداد ساخت solution، ORM و migration.
2. مدل فیزیکی tenant isolation، دسترسی ستاد و آزمون نفوذ بین کانون‌ها.
3. قرارداد identity/session و ماتریس نهایی تفویض دسترسی.
4. ارتباط ماژول‌ها، پردازش غیرهم‌زمان و workflow engine بر اساس بار و نیاز واقعی.
5. storage، پشتیبان‌گیری، بازیابی، monitoring و معیارهای ظرفیت/پایداری.
6. روش استقرار AI و اتصال امن آن؛ مدل/سخت‌افزار و چرخه آموزش/ارزیابی.
7. قواعد مالی، رضایت/نمایندگی خردسالان، محتوا، شاخص‌های ارزیابی و تأییدهای انسانی.
